● Informe de Auditoría Inicial — Complex.java (3792 líneas)
  1. Rendimiento (el hallazgo más grave)

  times/divides fuerzan una conversión polar→rectangular en cada operación:
  public Complex times(Complex that) {
      return new Complex('P', this.mod * that.mod, this.pha + that.pha);
  }
  El constructor 'P' ejecuta setRecCoord(), que llama a Math.cos+Math.sin para reconstruir rep/imp, más normalizePhase() y setCre(). Un multiply "textbook" (4 mults + 2 adds) aquí cuesta 2 funciones
  trascendentales + un bucle de normalización por cada llamada. Multiplicado por los bucles de gamma_euler/gamma_weiertrass (hasta 5×10⁷ iteraciones, línea 2518-2554) o zeta_havil, esto es el cuello de  
  botella dominante.

  plus/minus sufren el problema inverso: van por el constructor 'C' → setPolCoord() → Math.hypot+Math.atan2+normalización, aunque una suma no necesita el módulo/fase inmediatamente. Cada operación       
  aritmética, sea cual sea, recalcula ambas representaciones (rectangular y polar) más un quinto campo derivado (cre). Ese diseño "siempre-las-dos-representaciones" es la causa raíz de casi todo el      
  coste.

  Asignación masiva sin vía rápida in-place: cada operador retorna new Complex(...); no existe API mutable ni layout double[] intercalado para lotes, tal como pide el prompt. En los bucles de integrate()
  (3261-3417) y las sumas de zeta_re/gamma_* se instancian decenas de objetos Complex por iteración.

  Boxing evitable:
  public boolean isInfinite() { Double mod = this.mod(); return mod.isInfinite(); }
  Debería ser Double.isInfinite(this.mod), sin boxing.

  trunc(double, int) y round/getDecPart/getIntPart usan String.format + BigDecimal + Double.parseDouble para redondear — coste órdenes de magnitud mayor que aritmética de coma flotante pura, y frágil    
  (replace(",", ".") para sortear el locale).

  El regex de setComplex(String) se compila (Pattern.compile) en cada llamada en vez de usar un Pattern estático precompilado.

  Estado estático mutable global (EXACT, PRECISION, ZERO_THRESHOLD, REPRESENTATION, FORMAT_NBR…) hace que la aritmética dependa de un contexto global no thread-safe — incompatible con
  paralelización/Vector API tal como se pide. randomNbr es un único Random estático compartido (mejor ThreadLocalRandom).

  2. Rigor matemático

  - imPartNull()/rePartNull() dividen por el otro componente:
  public boolean imPartNull() { return Math.abs(imp/rep) <= ZERO_THRESHOLD*CORRECTION_FACTOR; }
  - Si rep == 0, imp/rep es ±Infinity o NaN (0/0) → el test puede devolver false para un número que en realidad es cero. Bug real de fiabilidad, no solo de estilo.
  - equals(Complex) no tiene hashCode() sobreescrito en toda la clase — viola el contrato equals/hashCode de Java; Complex en un HashSet/HashMap/.distinct() se rompe silenciosamente.
  - equals usa umbral absoluto (ZERO_THRESHOLD*CORRECTION_FACTOR ≈ 1e-12) independientemente de la magnitud de los operandos — sin escalado relativo/ULP, es demasiado laxo para números grandes y
  demasiado estricto para números pequeños.
  - power(Complex z) con this.mod == 0 colapsa siempre a comExp=comTri=0 sin distinguir 0^0, 0^(negativo) o 0^(complejo) — casos con semántica distinta según convención matemática, no gestionados.       
  - arcsin/arccos/arctanh usan las fórmulas ingenuas de libro de texto (log(z*i + sqrt(1-z²)), etc.) sin las salvaguardas de Hull et al. (1997) para evitar cancelación catastrófica/overflow de z² cerca  
  de los cortes de rama — el propio prompt pide auditar exactamente esto.
  - Los gamma_euler/gamma_weiertrass fuerzan iteraciones fijas (hasta 5×10⁷) en función de getMaxDecimals() en vez de comprobar convergencia real — ni garantiza precisión ni es eficiente. (gamma()       
  público ya usa gamma_fast/Lanczos, que es correcto y rápido — estos otros quedan como métodos "trampa" si se llaman directamente.)
  - Puntos positivos a conservar: setPolCoord() ya usa Math.hypot (evita overflow), y normalizePhase_1 sigue el rango (-π, π] estándar IEEE/C99.

  solo en casos extremos sino en casos moderados y comunes.

  Concretamente, para arccos(1.5) (real, >1): la fórmula actual da correctamente 0.9624i (verificado con roundtrip), pero la reformulación da -0.9624i — signo invertido. Lo mismo pasa en -0.4+0.6i,      
  0.4-0.6i, cerca de z=1, etc. La causa es el conocido "gotcha" de Kahan: sqrt(a)·sqrt(b) ≠ sqrt(a·b) para la rama principal compleja cuando arg(a)+arg(b) cae fuera de (-π,π] — exactamente lo que pasa   
  aquí para z>1 real (1-z es negativo real, 1+z positivo real). No es un error de transcripción mío; es una propiedad real de la rama principal de la raíz cuadrada compleja.

> investiga por qué no converge zeta_analytic_continuation cerca de un cero
● Confirmado con números duros — hay dos causas independientes que se combinan:
  Causa 1 — Complex.mONE.power(k-1) es cada vez más caro Y cada vez más impreciso. Para representar el signo alternante (-1)^(k-1), el código usa la potencia compleja general (log/exp + normalización de
  fase), no una simple comprobación par/impar. Como mONE tiene fase π, el ángulo intermedio crece como π·(k-1) — sin límite — y normalizarlo de vuelta a (-π,π] cuesta cada vez más (bucle while restando  
  2π) y acumula error de redondeo:

  ┌───────────┬──────────────────────┬───────────────────────────────────────────┐
  │     k     │ tiempo de la llamada │ resultado (debería ser exactamente -1+0i) │
  ├───────────┼──────────────────────┼───────────────────────────────────────────┤
  │ 1.000     │ 0,04 ms              │ -1.0 + 3e-11i                             │
  ├───────────┼──────────────────────┼───────────────────────────────────────────┤
  │ 1.000.000 │ 1,06 ms              │ -0.9999999994 + 3.4e-5i                   │
  ├───────────┼──────────────────────┼───────────────────────────────────────────┤
  │ 5.000.000 │ 4,06 ms              │ -0.99999993 - 3.7e-4i                     │
  └───────────┴──────────────────────┴───────────────────────────────────────────┘

  A los 5 millones de iteraciones, el "signo" ya tiene un error de 3.7×10⁻⁴ — muchísimo mayor que el umbral de convergencia (10⁻¹²). Ese ruido contamina z1 y puede impedir que el criterio de parada      
  (z1.equals(z2)) se cumpla nunca, sin importar cuánto se itere.

  Causa 2 — el criterio de parada exige un número irrealizable de términos para Re(s) pequeño. La serie alternante tiene términos ~1/k^Re(s); para que dos sumas parciales consecutivas difieran menos de  
  10⁻¹² hace falta:

  ┌─────────────────────────────────────────┬─────────────┐
  │                  Re(s)                  │ k necesario │
  ├─────────────────────────────────────────┼─────────────┤
  │ 2.0                                     │ ~10⁶        │
  ├─────────────────────────────────────────┼─────────────┤
  │ 1.0                                     │ ~10¹²       │
  ├─────────────────────────────────────────┼─────────────┤
  │ 0.7                                     │ ~10¹⁷       │
  ├─────────────────────────────────────────┼─────────────┤
  │ 0.5 (línea crítica, donde está el cero) │ ~10²⁴       │

 Contexto

 Complex.java (src/com/ipserc/arith/complex/Complex.java) mantiene toda su configuración de
 cálculo (EXACT, PRECISION, umbrales de cero, formato de salida, representación por defecto)
 como campos private static mutables, compartidos por todas las instancias y todos los
 hilos de la JVM. Esto es una idea pendiente documentada desde la Sesión 2 de revisión
 (Claude/ComplexArithRev.md), aparcada explícitamente por su tamaño hasta ahora.

 Un fork de exploración (esta sesión) confirmó el alcance real:
 - ~216 ficheros externos usan estos getters/setters, pero ~200 son TestComplex/* (tests, no
 librería). Solo 7 ficheros de librería real importan: MatrixComplex.java, Eigenspace.java,
 Polynom.java, Laplace.java, Fourier.java, Z.java, Spline.java.
 - El patrón dominante en esos 7 es storePrecision() → cambiar modo (exact(false),
 setPrecision(...)) → ejecutar un algoritmo que crea muchas instancias Complex anidadas →
 restorePrecision(). Esto requiere que el estado sea visible entre todas las instancias
 creadas dentro de la misma llamada, lo cual encaja con ThreadLocal (aislado entre hilos,
 compartido dentro del mismo hilo) y no con estado puro por-instancia.
 - Se encontró un bug de reentrancia preexistente (no relacionado con hilos): storePrecision/
 restorePrecision y setRepres/restoreRepres usan una única variable _BCK, no una pila —
 una llamada store→restore anidada dentro de otra pisa el backup externo. Decisión del
 usuario: no corregir este bug en esta fase, solo documentarlo en Javadoc (mismo patrón que
 otros bugs conocidos-no-corregidos ya presentes en el fichero).

 Decisión del usuario (vía AskUserQuestion): migrar a ThreadLocal manteniendo la API pública
 intacta — todos los getters/setters estáticos existentes (exact(), setPrecision(),
 setFormatON(), setRepres(), etc.) conservan firma y comportamiento. Ningún caller externo
 (ni los 7 de librería ni los ~200 de test) necesita cambiar una sola línea.

 Enfoque

 Todo el estado mutable pasa a vivir en una única clase interna State, respaldada por un único
 ThreadLocal<State>. Los campos que son constantes de fábrica (nunca reasignados tras la
 inicialización — verificado por grep: PRECISION_DEF, ZERO_THRESHOLD_EXACT_DEF,
 ZERO_THRESHOLD_APPROX_DEF, ZERO_THRESHOLD_DEF, SIGNIFICATIVE_DEF, DIGITS_DEF,
 MAX_DECIMALS_DEFAULT, LIM_NUMDECS, LIM_PRECISION, CORRECTION_FACTOR) se quedan como están
 — son inmutables en la práctica, seguros de compartir entre hilos sin cambios.

 Campos que SÍ se mueven a State (mutables, confirmado por grep de asignaciones fuera de la
 declaración — 23 campos en total, líneas ~221-261 del fichero actual):
 - EXACT, PRECISION, ZERO_THRESHOLD_EXACT, ZERO_THRESHOLD_APPROX, ZERO_THRESHOLD,
 SIGNIFICATIVE, DIGITS
 - PRECISION_BCK, ZERO_THRESHOLD_EXACT_BCK, ZERO_THRESHOLD_APPROX_BCK, ZERO_THRESHOLD_BCK,
 SIGNIFICATIVE_BCK, DIGITS_BCK
 - FORMAT_NBR, FIXED_NOTATION, SCIENTIFIC_NOTATION, MAX_DECIMALS
 - FORMAT_NBR_BCK, FIXED_NOTATION_BCK, SCIENTIFIC_NOTATION_BCK, MAX_DECIMALS_BCK
 - REPRESENTATION, REPRESENTATION_BCK

 Se mantienen los nombres de campo en mayúsculas (no camelCase) a propósito: reduce el riesgo de
 error de transcripción en una reescritura mecánica de ~23 campos × múltiples sitios de uso, y
 mantiene coherentes los comentarios/Javadoc existentes que ya los nombran así.

 Cada referencia suelta a uno de estos 23 nombres dentro del cuerpo de la clase (getters, setters,
 toString*, isZero, equals, divides, integrate, limit, etc. — dispersas entre la línea
 ~280 y ~4090) pasa a state().NOMBRE. Es una sustitución mecánica campo a campo, no un cambio de
 lógica: cada expresión que hoy lee/escribe el campo estático pasa a leer/escribir el mismo campo
 en state().

 Paso 2: reestructuración arquitectónica de Complex.java — split en paquete

 Contexto

 Complex.java (~4236 líneas) mezcla en una sola clase: aritmética core, parsing de strings, formato/presentación, cajas ASCII, configuración global (State), funciones especiales
 (gamma/zeta/trigonometría) e integración/límites. Desde la sesión 2 está pendiente una reestructuración arquitectónica "de programador senior" separando responsabilidades. El usuario ya decidió (Sexta  
 sesión): split en varias clases dentro del mismo paquete com.ipserc.arith.complex, con la API pública de Complex intacta al 100% (la usan MatrixComplex, Eigenspace, Polynom, Laplace, Fourier, Z, Spline 
 y ~200 test files).

 Un agente de exploración mapeó el acoplamiento real entre secciones antes de diseñar el split (evitando un plan genérico). Hallazgo clave: solo el bloque de cajas ASCII (boxTitle*/boxText*) tiene

 - Las funciones especiales/trigonometría/integración/límites/round tocan campos privados directamente (z.rep, point.mod, etc.) de instancias Complex que reciben como parámetro — no solo de this. Mover

 - normalizePhase() (definido bajo el banner "PRESENTATION" pero es en realidad un invariante de aritmética) lo usan tanto Presentación como la Aritmética core (operaciones in-place). Debe quedarse en   
 el núcleo, no en el formateador.

  Cómo están implementadas ahora (ComplexFunctions.java):
  static Complex tan(Complex z)  { return sin(z).divides(cos(z)); }
  static Complex cot(Complex z)  { return cos(z).divides(sin(z)); }  static Complex tanh(Complex z) { return sinh(z).divides(cosh(z)); }
  static Complex coth(Complex z) { return cosh(z).divides(sinh(z)); }

  Y sin/cos (con z=x+iy) están implementadas así:
  sin(z) = sin(x)·cosh(y) + i·cos(x)·sinh(y)
  cos(z) = cos(x)·cosh(y) − i·sin(x)·sinh(y)

  El problema: ambas fórmulas usan exactamente los mismos 4 valores reales — sin(x), cos(x), sinh(y), cosh(y). Al llamar a tan(z) = sin(z).divides(cos(z)), se calculan esos 4 valores dos veces (una      
  dentro de sin(z), otra dentro de cos(z)), y encima se hace una división compleja completa (más cara que una división real).

  La alternativa (identidad de ángulo doble, la demostré algebraicamente para confirmar que es correcta):
  tan(x+iy) = [sin(2x) + i·sinh(2y)] / [cos(2x) + cosh(2y)]
  Esta fórmula solo necesita 4 llamadas trascendentales (sin(2x), cos(2x), sinh(2y), cosh(2y)) — la mitad — y el denominador cos(2x)+cosh(2y) es un número real, así que dividir es una división real      
  simple (numerador real/denominador, numerador imaginario/denominador) en vez de una división compleja general. Para tanh hay una identidad análoga: tanh(x+iy) = [sinh(2x)+i·sin(2y)] /
  [cosh(2x)+cos(2y)]. Y cot/coth se pueden definir simplemente como 1/tan(z) y 1/tanh(z) reutilizando esas versiones optimizadas, en vez de repetir el mismo patrón duplicado con cos(z)/sin(z).

  El problema: TestIntegral01 integra log(x) de -1 a 1. El punto medio de ese intervalo es exactamente x=0 — una singularidad (integrable, el valor real de la integral es finito, -2+πi). La suma de
  Riemann antigua, por cómo acumulaba el paso sumando repetidamente, por casualidad de redondeo en coma flotante nunca caía exactamente en x=0, así que daba una aproximación razonable (-2.004+3.142i). Mi  Simpson, al parametrizar cada punto de forma independiente (punto = a + t·(b-a)), cae exactamente en el punto medio para cualquier n par que pruebe — no es cuestión de subdividir más, siempre lo toca.
  Resultado: log(0)=-Infinity contamina toda la suma, y el test ahora da -Infinity en vez de un valor finito.

  mejorar aunque pida más decimales) por una singularidad logarítmica en su propio límite inferior — esto no es nuevo, ya era igual de impreciso antes, solo que ahora lo puedo demostrar claramente.

> empieza por el de log()
● Diagnóstico confirmado con precisión matemática. El problema de fondo:

  logTaylor() reduce la matriz dividiendo por ||A|| (norma de Frobenius, un escalar real positivo), y luego expande log(1-x) con x = I - A/||A||. Esa serie solo converge si el autovalor de x tiene módulo  < 1 — lo cual solo pasa si el autovalor dominante de A es un real positivo cercano a +||A||. En cuanto el autovalor se aleja de esa dirección (negativo, complejo, o simplemente de signo distinto),     
  diverge.

  Verificado exactamente con A=[[-50,1],[0,-50]] (autovalor -50): ||A||=70.72, autovalor de x resultante = 1.707 (fuera del disco unidad → diverge, exactamente el caso que reprodujo el fork). Con el
  mismo Jordan pero autovalor +50: autovalor de x = 0.293 (converge sin problema). Es decir: el cambio de variable x = I - A/||A|| solo es válido cuando el autovalor dominante está cerca de +||A|| en el
  plano complejo — no es un problema de magnitud, es de signo/fase relativo a un escalar siempre positivo.

  Esto es exactamente lo que describiste. Con esto claro, hay dos niveles de arreglo muy distintos en coste/riesgo:

● Los problemas reales, en orden de importancia:
  1. Necesita una raíz cuadrada de matriz, que no existe todavía. El scaling-and-squaring inverso es: tomar √A varias veces hasta que los autovalores queden cerca de 1, sumar ahí la serie (que sí
  converge), y deshacer: log(A) = 2^s·log(A^(1/2^s)). Pero calcular √A para una matriz genérica (compleja, posiblemente defectuosa) es en sí mismo un problema no trivial:  - Tiene múltiples raíces (igual que √-1 = ±i en escalares) — hay que elegir la "principal" de forma consistente, el mismo tipo de decisión de corte de rama que tanto os ha ocupado en Complex.java.
  - El método estándar y estable (Björck–Hammarling, vía descomposición de Schur) necesita justamente una descomposición de Schur — que existe en el proyecto (Schurfactor.java) pero está sin terminar y  
  sin commitear (visto en el inventario de la pila sin trackear). Sin ella, un método más ingenuo de raíz cuadrada puede ser inestable precisamente para las matrices defectuosas que es las que queremos
  arreglar.

  2. ¿Cuántas raíces cuadradas son suficientes? Hace falta un criterio para decidir cuándo parar (¿autovalores ya "cerca" de 1?). Si ese criterio se basa de nuevo en la norma de Frobenius en vez de en   
  los autovalores reales, se puede acabar reintroduciendo la misma clase de problema que estamos arreglando, solo que más disimulado.

  3. Amplificación de error. Cada raíz cuadrada acumula su propio error de redondeo; al final se deshace multiplicando por 2^s. Con varias raíces necesarias, ese error se amplifica por un factor
  creciente — es un trade-off de estabilidad numérica conocido de esta familia de algoritmos, y aquí sería peor que en el exp() ya existente porque el "deshacer" es una multiplicación, no una división.  

  4. Consistencia de rama a través de las raíces. El logaritmo de matriz es multivaluado (cada autovalor tiene infinitas ramas, +2πik). Hay que garantizar que cada raíz cuadrada sucesiva elige la rama   
  compatible con las anteriores, o el resultado final puede ser numéricamente estable pero matemáticamente en la hoja equivocada — un bug silencioso muy difícil de detectar por inspección.

  5. Verificación mucho más débil. Los fixes anteriores (pivoteo, exp()) se pudieron verificar contra un valor analítico exacto independiente (fórmula cerrada de Jordan, inversa 2×2 a mano). Para el     
  logaritmo de una matriz defectuosa genérica con varios bloques de Jordan de tamaños/autovalores distintos, no hay un oráculo tan limpio — habría que confiar mucho más en "no dio NaN" que en "coincide  
  con el valor exacto".

  6. Alcance real desconocido. No sabemos todavía si algún caller real del proyecto llama a log() sobre una matriz genuinamente defectuosa en la práctica (fuera de los tests sintéticos que hemos
  construido para diagnosticar el bug) — podría ser esfuerzo considerable en una ruta que casi nunca se ejercita de verdad.

  En resumen: no es un "fix", es más bien un pequeño proyecto de implementación numérica con su propia superficie de bugs nueva (incluida la de raíz cuadrada de matriz, que aún no existe). Mi
  recomendación sigue siendo la opción 1 (que la serie falle alto en vez de mentir) como base sólida ahora, y dejar esto como una iniciativa aparte si en algún momento quieres abordarla con calma.
